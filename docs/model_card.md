# Model Card - Bank Marketing Classifier (BancoX)

## Intended Use
Predecir si un cliente se suscribirá a un depósito a término (variable objetivo `y` del dataset Bank Marketing).
Intended users: equipos de marketing, analistas de datos y científicos de datos que evalúan y priorizan clientes para campañas.
Limitations: puede reflejar sesgos demográficos (edad, tipo de trabajo, nivel educativo). No usar como única fuente para decisiones automatizadas que afecten derechos de clientes.

## Model Details
- Algoritmo principal: XGBoost (`XGBClassifier`) según el código de entrenamiento (`mvp_para_frontend.py` y notebooks).
- Balanceo de clases: SMOTE (imbalanced-learn).
- Reducción dimensional: PCA aplicada como paso opcional en el pipeline.
- Serialización / tracking: el proyecto soporta registro con MLflow (runs en `./mlruns`) y guarda artefactos (modelos, curvas, CSVs). En ejecuciones locales típicas el modelo se serializa como `model.pkl`/`model.joblib` dentro de la carpeta `models/` o se registra como artefacto de MLflow.

## Data & Preprocessing
- Fuente: UCI Bank Marketing Dataset (https://archive.ics.uci.edu/dataset/222/bank+marketing) combinado con transformaciones internas usadas en los notebooks.
- Transformaciones aplicadas en el código:
  - Limpieza y remoción de outliers en variables numéricas.
  - Codificación de variables categóricas (one-hot / label-encoding según variable).
  - Escalado/normalización de features numéricos cuando aplica.
  - Balanceo con SMOTE en el set de entrenamiento.
  - Reducción de dimensionalidad con PCA (opcional, configurable en el pipeline).
- División de datos: split entrenamiento / test 80/20 (definido en los notebooks y scripts de entrenamiento).

## Training & Validation
- Validación: evaluación sobre set de test separado (20%) y generación de curvas ROC/PR, matrices de confusión y CSVs con métricas (`metrics.csv`).
- Tracking: llamadas a `mlflow.log_param`, `mlflow.log_metric` y `mlflow.log_artifact` están previstas en el pipeline para trazar parámetros, métricas y artefactos.

## Bias & Fairness
- En el análisis exploratorio y los reportes se observan diferencias en tasa de aceptación por grupos de edad, tipo de trabajo (`job`) y nivel educativo (`education`).
- Recomendaciones para mitigar sesgos:
  - Evaluar métricas por subgrupos (por ejemplo, F1/recall por tramo etario y por `job`).
  - Considerar técnicas de recalibración o reweighting si se detectan disparidades significativas.
  - Mantener logs de decisiones cuando el modelo se use para priorización humana y revisar casos con intervención humana.

## Deployment & Rollback
- Despliegue actual en repo:
  - Imagen Docker sugerida: `banco-x-api` (comandos en README para build/run).
  - Frontend / dashboard: `frontend.py` y `dashboard_seguimiento.py` (Streamlit) para monitoreo y visualización.
  - API: ejemplos de endpoint `/predict` y `/batch` documentados en README; la imagen expone puerto 8000 en los ejemplos.
- Comandos Docker (ejemplo):
```bash
docker rm banco-x-api
docker build -t banco-x-api .
docker run -d --name banco-x-api -p 8000:8000 banco-x-api
```
- Rollback: detener el contenedor en producción y ejecutar la versión previa etiquetada. Ejemplo sencillo:
```bash
docker stop banco-x-api
docker rm banco-x-api
docker run -d --name banco-x-api -p 8000:8000 banco-x-api:<previous-tag>
```
- Observabilidad: usar MLflow UI (`mlflow ui --backend-store-uri ./mlruns --port 5000`) y los CSVs generados por el pipeline para validar comportamiento tras deploy.

## Caveats & Recommendations
- Antes de la puesta en producción completa, validar en un ambiente de staging y ejecutar pruebas A/B o pruebas de regresión para verificar que la performance se mantiene con datos en producción.
- Mantener versionado del modelo (tags de Docker y/o modelos en MLflow) y registros de datos utilizados para entrenamiento para garantizar trazabilidad.
- Revisar cumplimiento regulatorio y privacidad antes de aplicar scores de forma automatizada sobre clientes.
